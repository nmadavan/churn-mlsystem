# Design Notes — Churn Mini Production ML System

Running log of decisions, measured results, and trade-offs. Source material for the
final design document. Updated at the end of each build session.

---

## 1. Problem and metrics

- **Task:** binary classification — predict whether a telco customer will churn.
- **Users / use case:** retention team. Two consumption modes: an on-demand risk score
  when an agent opens a customer profile (online), and a nightly score of the whole base
  for campaign targeting (batch).
- **Target:** `Churn` (Yes/No). Positive class = churn = "Yes".
- **Class balance:** ~26.5% churn (1,869 / 7,043) — imbalanced, which drives metric choice.
- **Metrics chosen:** ROC AUC (headline, threshold-independent ranking), PR AUC / average
  precision (informative under imbalance, focuses on the churn minority), F1, precision,
  recall. Accuracy reported for context only — predicting "no churn" for everyone already
  scores ~73.5%, so accuracy alone is misleading.
- **Why recall matters here:** missing a churner (false negative) costs a lost customer;
  a false positive costs a cheap retention offer. Recall is weighted accordingly.

## 2. Data and features

- **Source:** `telco_churn.csv`, 7,043 rows, 21 columns.
- **Cleaning decisions:**
  - `TotalCharges` arrives as text because 11 brand-new customers (tenure=0) have a blank.
    Decision: coerce to numeric, fill blanks with **0.0** (never completed a billing cycle).
  - Drop `customerID` (identifier, no signal).
  - Map target to 1/0.
- **Engineered features (6 non-trivial):** `num_addon_services` (count of 6 add-ons),
  `charges_per_tenure_month` (ratio, +1 guards divide-by-zero), `monthly_to_total_ratio`
  (ratio, front-loaded-spend signal), `is_month_to_month` (highest-risk contract, 42.7%
  churn in EDA), `has_fiber` (fibre churns more), `tenure_bucket` (churn falls steeply by
  tenure band: 52.9% at 0–6mo → 9.5% at 49+mo). After one-hot + scaling: **55 features**.
- **Offline vs online:** all 6 engineered features are row-local math computable from a
  single request — no historical lookup needed, so there is no offline/online split to
  reconcile. If a feature needed history (e.g. "support calls last 30 days"), that would
  require a feature store / precompute-and-lookup; discussed as a contrast in the doc.
- **Train–serve skew defence:** `src/preprocessing.py` is imported by BOTH training and
  serving (via the saved sklearn Pipeline). Identical code path offline and online.
  A test (`test_serving_row_matches_training_width`) asserts a single request transforms
  to the same 55 columns as training.
- **Data quality — two-level guardrail in ingestion:**
  - File level: schema mismatch (column added/removed/renamed) → whole file rejected.
  - Record level: bad rows quarantined to `data/rejects/<file>_rejects.csv` with a
    `reject_reason`; good rows still ingested (no whole-batch abend). Reject rate per batch
    is logged → becomes a data-quality signal for monitoring.
  - Domain-aware: a blank `TotalCharges` on a tenure=0 row is valid, NOT quarantined.

## 3. Model and evaluation

- **Baseline:** Logistic Regression (`class_weight="balanced"`, scaled features).
- **Candidate:** Random Forest (300 trees, `class_weight="balanced_subsample"`).
- **Split:** stratified train/val/test = 4,507 / 1,127 / 1,409 (keeps ~26.5% churn each).
- **Validation results:**

  | Metric | Baseline (LogReg) | Candidate (RF) |
  |--------|-------------------|----------------|
  | ROC AUC | **0.8525** | 0.8286 |
  | PR AUC | 0.6814 | 0.6297 |
  | F1 | 0.6341 | 0.5494 |
  | precision | 0.533 | 0.6715 |
  | recall | **0.7826** | 0.4649 |
  | accuracy | 0.7604 | 0.7977 |

- **Promotion guardrail:** promote candidate only if ROC AUC ≥ 0.80 AND not worse than
  baseline by more than 0.01. **Result: candidate NOT promoted** (0.8286 < 0.8525 − 0.01).
- **Key finding:** the simpler baseline won. On well-engineered tabular features, logistic
  regression was competitive; the RF had higher accuracy but much lower recall (0.46 vs
  0.78) — worse for catching churners. The guardrail correctly prevented a regression.
- **Winner (LogReg v1) held-out test metrics:** ROC AUC 0.8469, PR AUC 0.659, F1 0.6134,
  precision 0.5052, recall 0.7807, accuracy 0.7388. Test ≈ validation → no severe overfit.
- **Registry:** file-based. `models/v<N>/` (model.pkl + metadata.json) + `current_best.json`
  pointer. `.pkl` is gitignored (build output, regenerated by `python -m src.train`);
  metadata + report committed as evidence.

## 4. Serving and inference pattern (hybrid)

- **Online:** FastAPI `/predict` (+ `/health`). Pydantic validates the request (missing
  field → HTTP 422). Loads the promoted model once at startup (lifespan). Returns
  prediction + probability + model_version.
- **Batch:** `scripts/batch_score.py` scores a whole CSV in one vectorised pass.
- **Model size:** 10 KB (LogReg = 55 coefficients + 1 intercept) → loads in ms, no GPU.
- **Measured performance:**
  - Batch: 7,043 rows in 0.032s → **~220,000 rows/sec**. Predicted churn 2,850 / 7,043.
  - Online (300 requests): avg **6.60 ms**, p50 6.35, **p95 7.78**, p99 9.53, max 45.70 ms,
    ~151 req/sec sequential.
- **Inference-pattern justification (M2):** batch is ~1,400× more efficient per row (no
  per-request HTTP/JSON/validation overhead), so use it when no human waits (nightly
  scoring). Online 6.6 ms is well under the ~100 ms "instant" bar, right for a human-waiting
  lookup. Hybrid = each pattern serves a distinct real use case.
- **Trade-off noted:** p95 (7.78 ms) and max (45.70 ms) > avg (6.60 ms) — report percentiles,
  not just the average, because tail latency is what users feel.

## 5. Containerization (Docker)

- `Dockerfile` on `python:3.12-slim` + `libgomp1` (OpenMP for sklearn). Trains the model
  **during the build** → fully self-contained, no dependence on local artifacts.
- Layer order (requirements before code) leverages build cache.
- `HEALTHCHECK` hits `/health` via stdlib. `CMD` binds uvicorn to `0.0.0.0:8000`.
- **Verified:** container `/predict` returned 0.8724 — identical to the local server.
- Image size ~529 MB.

## 7. Key trade-offs, limitations, future work
- Simpler model chosen over complex one — favours interpretability + recall over raw
  accuracy. Justified for churn.
- Decision threshold fixed at 0.5; could be tuned to the retention budget (precision/recall
  trade-off) — future work.
- File-based registry, not a server (MLflow) — sufficient at this scale; a real system would
  use a tracking server + artifact store.
- No feature store — not needed because all features are row-local; would be required for
  history-based features.
- Single-node, single-model — no autoscaling/multi-tenant concerns addressed.
